## 2. V2 boundary and shared contract rules — proposals

### 2.1 Execution boundaries

| Interaction type | Proposed execution path | What must stay out of the client |
|---|---|---|
| Server-rendered page/layout read | Next server page/layout → server-only frontend adapter → authorized NestJS read API → sanitized view model | Bearer token, DB credentials/names, Prisma user rows, support tokens |
| Submit/command | Client form/confirmation → **thin Next Server Action** → authorized NestJS command API → normalized result → explicit invalidation/refresh/optional navigation | Business transactions, role/relationship decisions and financial arithmetic belong in NestJS, not copied V1 actions |
| Tabs/dialogs/unsaved drafts/filtering a complete loaded dataset | Client state/derived values | No Server Action or API mutation. If full dataset is not loaded, query controls trigger a read adapter, not fake local completeness |
| Audit pages, server search/pagination, manual dashboard refresh | URL/search state or same-origin read transport → server-only adapter → NestJS GET | No command merely to read; no token passed into client fetch headers |
| Bell polling | Client polls proposed same-origin web GET `/api/gyms/:slug/notifications` → server adapter reads HttpOnly session → NestJS notifications GET | Token stays server-side; polling GET does not mark read |
| Notification mark one/all | Thin Next Server Action → authorized NestJS mark command → explicit result and bell reread | No hidden mutation on GET; derive recipient from identity |
| Authenticated CSV | Browser navigates proposed same-origin web download route → server-only adapter → authorized NestJS export → streamed bytes/attachment | Do not put bearer token in URL, browser storage or downloadable CSV. Web route repeats access checks and uses no-store |
| Initial brand/theme read | Server layout → public theme endpoint or authorized extended appearance adapter | Raw arbitrary CSS/HTML/font URLs must not become client-executable theme content |

The proposed web `/api/...` transports above are **new web routes**, not current NestJS endpoints. Current V2 already uses thin web actions for login/createGym/basic createMember and server fetches with `cache:'no-store'`; see `V2/apps/web/src/app/actions.ts:17`, `:71`, `:106` and `app/gyms/[slug]/page.tsx:32`. Preserve that separation.

Master identity/access/theme/platform reads and tenant operations remain behind API boundaries; no frontend cross-database join.

### 2.3 Proposed common transport shapes, errors and pagination

These are contract descriptions, not code files or current API responses:

```text
Read<T> = { data: T, meta: { requestId, asOf: ISOInstant, gymSlug?, currency?, timeZone? } }
Page<T> = { items: T[], page: integer>=1, pageSize: integer, totalCount, totalPages, asOf,
            summary?: domain totals over the FULL filter, not the visible page }
Command<T> = { ok: true, operationId, data: T, replayed: boolean,
               effects: { changedResourceIds, refreshScopes: string[] } }
Failure = { ok: false, code, message, fieldErrors?: Record<field,string[]>,
            requestId, retryable: boolean, operationId?, retryAfterSeconds?,
            currentState?: { resourceId, status, version } }
Money = { amount: decimal-string, currency: ISO4217-code }
```

Proposed read pagination: page/pageSize, stable secondary ID sort; default 25 (audit 20), max 100; validate bounds and filters with 400. Return totals/summary computed before paging; all-page CSV is an explicit export scope. No current V2 member paging/search contract exists. Filters below use enumerated status, `q` bounded to 200 characters, valid ISO local dates/months, bounded period and page size. Never silently coerce invalid dates to an unrelated month. Ranges are gym-local dates converted by API into `[start,endExclusive)` instants. Date of birth stays a date string, not a browser-timezone-shifted instant. Each gym selects currency and IANA time zone at creation; currency is locked after financial activity. Exact precision, rounding and DST input rules are proposed pending technical review (section 14).

Every protected proposed contract returns 401 for missing/expired identity,403 for role denial/required password change (`PASSWORD_CHANGE_REQUIRED`) or forbidden context,404 for missing/out-of-scope nested resource (avoid cross-gym enumeration),400 for malformed input,409 for duplicate/stale state/collision/idempotency mismatch,422 for domain rejection (no credit, too early, invalid transition),429 with retry delay,503 for unavailable dependency. Safe error messages only; transport/network failure is distinguished from definitive command rejection. Do not automatically resubmit when outcome is unknown. Existing APIs currently use Nest exceptions/plain objects, not this envelope; adapters must normalize them until a separately agreed API evolution.

### 2.4 Repeat submissions, secrets and refresh

**Proposed requirement:** all create/financial/lifecycle commands accept `Idempotency-Key` plus `expectedVersion` for mutable resources where available. Scope key to identity + effective gym/support context + operation + request hash. Same key/body replays the committed operation/result, with **no additional credit, revenue, pay, audit or notification effects**; changed body/key scope mismatch 409. Stale version/invalid terminal transition 409 or 422 with current state. Different-key duplicate intent still needs domain duplicate detection; an idempotency header alone does not prevent it. This is not evidenced in current V1 or V2 handlers. D01–D06 and D10–D13 govern business choices.

Commands return resource versions and refresh scope hints. Web adapters use a reviewed fixed mapping (section 12), never blindly invalidate arbitrary paths from an API string. Private cache keys include identity/access context, gym, role/view/filter/pagination; no cross-gym/global cache of privileged reads. Begin with no-store where correctness matters. Current V2 has no feature tag cache; current V1 path invalidation is incomplete, recorded separately. Cross-role updates require next read/poll or an agreed event delivery contract, not just initiating user's `router.refresh()` (Open D17).

Registration secrets are an explicit exception to ordinary replay: first authorized response can contain a temporary password for display only; no logs, URLs, caches, audit, notification text, browser storage or subsequent profile/read responses. Duplicate registration must not generate another identity/password. If the first response is lost, return an operation/delivery state without secret and use an approved recovery/rotation process; one-time delivery and authorized rotation are approved; exact expiry and acknowledgment mechanics need security review, not plaintext caching. Web keeps the result in component memory for handoff, then clears it on exit/logout/context switch.

### Cross-cutting localization and identity decisions

V1 uses `$`, sometimes en-US and sometimes browser locale; date-input “today” sometimes uses UTC `toISOString`, session parsing uses server-local `new Date(date+'T'+time)`, dashboard windows use server-local midnight, chart days sometimes UTC, and native inputs display browser locale. No gym currency/timezone selector exists in current UI/API. Proposed C06 supplies `{currency,timeZone,locale,formatVersion}` for all reads/commands; amount is Money and scheduled datetime has a declared gym zone/offset. Date/time and monetary interpretation must be API-authoritative, with explicit bounds and DST ambiguity errors, not chosen by frontend deployment timezone (D07/D08). Current E04/E06 cannot supply this metadata.

The profile's fullName/member health fields must not be inferred from current V2 identity email. Auth response lacks display name and tenant actor IDs. C01/C06 must supply sanitized role-specific identity/actor mapping. No master or tenant schema change is designed here.

### Shared V1 pack/pricing behavior requiring an explicit V2 contract

`V1/actions/sessions.ts:133` selects a currently ACTIVE positive-balance pack by **earliest expiry**, without requiring expiry>now and without binding the booking to that original pack. It decrements remaining by read-then-set, marks EXHAUSTED at zero, and always creates recognized revenue using stored session.fee. No pack at consumption time does not itself reject completion/no-show/late cancellation. Booking/request merely check credit at creation; acceptance does not reserve/recheck it. Different bookings can be made against the same available balance. Whether those facts produce overdraft/lost updates under concurrency is untested; they are contract risks, not guarantees.

`V1/lib/pricing.ts:24`, `:36`, `:53`, `:68`:pack price/total takes precedence; otherwise INTRODUCTORY override then LEVEL_2 override then default; round2 at fee boundary. Trainer pay = round2(fee×(current level base + current off-shift premium if stored shift says OFF_SHIFT)). Shift test `time<start || time>end` is string comparison and does not handle overnight shifts like analytics' separate calculation. Settings copy promising frozen pay at session start is not established by W19, which reads gym/trainer at completion. D06/D08/D10 must settle entitlement selection/reservation/expiry, money/pay snapshots and timing; frontend sends no authoritative fee, credited pack or pay amount.

### 8.1 EV01 — isolated V1 optional-rate validation evidence

On 23 October 2026, Node v20.19.0 loaded **V1's installed Zod 3.25.76** (`V1/node_modules/zod/package.json`; also locked in `V1/package-lock.json:7874`). The exact `rateCardSchema` text was extracted from `V1/actions/gym-config.ts:149`–`:153` and evaluated with that Zod instance. The form helper's normalization and the action's extracted update-value expression (`:169`–`:172`, `:190`–`:191`) were checked in isolation. With defaultSessionFee=`"75"`, blank, whitespace and absent optional form fields all normalized to `""`, parsed to `{defaultSessionFee:75,level2SessionFee:0,introSessionFee:0}`, and selected **0** for the update payload. Explicit `"0"` also selected 0; `"45"` selected 45; `"-1"` failed validation.

`z.union([z.coerce.number().min(0), z.literal("")]).optional().parse("")` returns **0** here; the literal-blank branch is not reached. This resolves the former tentative inference. The action's source therefore writes zero on a successful blank submission, despite its comment/UI copy about standard fallback. **No action/module with application side effects, Prisma client, database, HTTP endpoint or browser workflow was invoked.** Database persistence and end-to-end saving remain unverified. Proposed C41 intentionally changes blank→null→standard fallback while preserving explicit 0. EV01 is evidence for the V1 pure validator only; AT06 is a future V2 acceptance requirement.

### 10.2.1 C10 derived billing history — exact proposed read contract

**V1 source baseline:** `V1/dashboard/owner/members/[id]/page.tsx:23`–`:33` loads all memberships (created-desc) and all packs (created-desc). `member-profile-client.tsx:26`, `:268`–`:318` renders **only the first/latest-created membership**, then **every pack**, including inactive/exhausted/expired packs. Membership display date=startDate and amount=its joined plan.price; pack display date=purchaseDate and amount=price or0. Both display a hardcoded PAID badge; receipt buttons alert. There is no payment query, payment verification, paging or older-membership billing row. W32 desk-payment revenue is not loaded here. This is source-verified display behavior, not proof of payment.

**Proposed C10 composition and bounded response (not implemented):**

- Candidate rows are **one latest-created membership, if any, plus every pack of this same-gym member across all statuses**. Do not include other memberships, desk-payment revenueRecords, session-consumption revenue, payroll or unrelated members. Compute this candidate set from the complete authorized sources, **independently of membershipPage and packPage**, not their returned slices. Latest membership is selected by createdAt-desc then id-desc; this stable tie-break is proposed.
- Preserve the V1 grouping: the single membership row first, then packs by createdAt-desc then id-desc. The displayed startDate/purchaseDate is not the sort key. Apply pagination **after** composing/sorting this union; the membership appears once, not pinned again on every page.
- `DerivedBillingPage = {source:'membership-and-pack-history',items:BillingHistoryRow[],page,pageSize,totalCount,totalPages,asOf}`. Here page/pageSize echo billingPage/billingPageSize (default 1/25, max 100). totalCount=(latest membership exists?1:0)+**all** pack rows for this member; totalPages=ceil(totalCount/pageSize),0 when empty. A syntactically valid page beyond the last returns empty items with accurate totals; malformed/nonpositive/oversize query400. No unbounded `items` and no total inferred from the visible page.
- `BillingHistoryRow = {rowId,sourceKind:'MEMBERSHIP' or 'PACK',sourceId,displayDate,description,sourceStatus,amount:Money,amountMissing:boolean,amountBasis:'MEMBERSHIP_AGREED_PRICE' or 'PACK_ISSUE_PRICE',paymentStatus:null,receiptAvailable:false}`. rowId is `membership:<id>` or `pack:<id>`. Membership amount uses its immutable agreed-price snapshot; pack amount uses its issue-price snapshot. Fresh V2 records require explicit prices, including valid zero; any missing legacy value is marked unavailable rather than presented as paid zero. Dates and amount currency follow C06/D07/D08. **V2 display correction:** label this derived membership/pack history, without treating V1's hardcoded PAID badge as verified payment evidence; no real receipt is promised.
- O04 Payments/history Next/Previous changes billingPage in the URL and rereads C10 through `R/members#getMemberProfile` (section 12.2); **no Server Action**. Preserve billingPageSize and other tab/source-page queries. This reaches every older pack row. Older membership records are deliberately outside this V1-derived billing list; the proposed Overview membership-history pager reaches them through C10 via membershipPage. This read-navigation affordance is proposed, not a V1 billing row/control. They are not silently inserted as payments.
- Pack issue/registration invalidate **all C10 billing/source-page variants** for the member (section 12). Payment recording is future scope; this derived list is not a payment ledger. A future linked ledger/receipt contract requires its own design; it must not be simulated by inserting an invented PAID row. Paging never widens O+G/member authorization.

## 11. Command contracts — V2 proposals and explicit outcomes

**All C command routes below are proposed**, except C05 which expands the **insufficient existing** E04/E05 surface. E01/E03/E08 remain existing only for section 3's exact DTO/behavior. Every proposed command requires section 2 authorization, strict request schema (reject unknown fields), common errors, idempotency/repeat semantics, and explicit result/refresh. An API may be implemented later under different reviewed paths; the endpoint labels must change only after source verification.

Proposed input normalization: trimmed names 1–120, email normalized/validated≤254, registration phone required, 1–40 characters, descriptions/notes≤4000, IDs nonempty bounded strings; do not trim passwords. Dates must be real dates; DOB not future (age restriction D03), local times HH:mm plus declared gym zone/offset. Counts/durations/days must be positive integers (specific maxima D06/D12); amounts decimal strings with supported currency/precision D07, not binary float from client. Numeric zero is preserved; **C41 intentionally changes V1 blank optional-rate behavior** by normalizing blank to explicit null/standard fallback (EV01 verifies V1 blank→0). Rates proposed fractions 0..1 with combined base+premium≤1 unless Finance decides otherwise. Meal enum uses the six rendered selector values; expose canonical allowed values in schema rather than accept arbitrary strings. Proposed request row/array maximum 100, field/numeric limits must be approved/tested, not treated as V1 facts.

Audit/notification obligations in the workflow tables describe V1 calls. For V2, return authoritative operation outcome only after core state/credit/revenue/pay consistency is known. Durable audit/notification status must be defined (D16/D18); a post-commit notification failure must not invite duplicate financial execution. Never claim an idempotency header makes several independent databases atomic. Provisioning/identity enrollment failure/recovery needs an explicit operation result (D03/D13).
