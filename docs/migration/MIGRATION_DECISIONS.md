## ADR and change-control format

Use `DEC-ID`, date, proposal author, actual approving reviewer, source map references, settled constraints, options/tradeoffs, selected outcome, explicit numeric/input/time/rounding limits, affected task/API/schema/test IDs, migration/compatibility consequences and acceptance examples. A recommendation stays Proposed until reviewed. Architectural change requires a concrete proposal and project-owner approval; routine implementation within signed constraints needs no new approval. Update the authoritative task specification and all derived tracker/dependency/traceability views in the same documentation change. Never reuse task IDs.

GYMOS-MIG-002 owns common contracts/triage; GYMOS-MIG-077–GYMOS-MIG-088 own focused decision records. These decision tasks do not authorize production deploys or database resets. Product-owner decisions on early suspension earning/expired-unused recognition may explicitly choose separate unavailable report lines for MVP; do not invent an accounting event while waiting.
