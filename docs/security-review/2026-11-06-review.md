# GymOS V2 security review — 6 November 2026

## Verdict and boundaries

The reviewed implementation has substantial authentication, authorization, transaction and tenant-binding safeguards. It also has actionable gaps in registration identity assurance, legacy token enforcement, abuse protection and browser hardening. This review does not certify the application secure or ready for public use. No unauthenticated arbitrary cross-gym data-access or SQL injection exploit was demonstrated.

Scope: active gymos-v2 workspace, not a complete V1 audit. Reviewed authentication and refresh, account recovery, application registration, controller permissions, tenant binding, support access, browser transport, sensitive projections, database configuration, SQL construction, logging, exports and CI. Read-only analysis plus isolated tests; no product fixes. Other ongoing workspace edits were preserved. A snapshot review can become stale as files change.

No real user data or production service was tested. No live browser penetration test, exhaustive endpoint fuzzing, infrastructure inspection, secret-history scan or load test was performed. Dependency advisory lookup was blocked and then declined by the user to keep package metadata private; no clean-dependency claim is made.

## Findings

### S1 — High: public registration does not verify email ownership

Evidence: apps/api/src/member-applications.service.ts:20–45; apps/api/src/auth.controller.ts login; master User schema has no verified-email gate.

An unauthenticated applicant supplies an email address and password. The service immediately creates a global User with that password and an application. Login does not require proof of inbox ownership. Existing email addresses receive a neutral response, which helps avoid enumeration and does not overwrite an existing password.

A person can nevertheless reserve another person's unused address and log in as that newly created account. Owner approval is still needed for gym access, so this is not automatic access to a gym or takeover of an already-existing account. Misidentification during approval can turn the false identity into operational access; even without approval, the legitimate address holder faces an account-recovery problem.

Fix: introduce short-lived pending registration and single-use email verification; mark verified ownership explicitly; require it before account activation/approval and identity reuse. Handle expired or malicious pending reservations without permanently blocking the address. Keep uniform responses. Test both existing accounts and competing registrations.

### S2 — Medium: legacy tokens skip revocation checks on account routes

Evidence: apps/api/src/identity/auth-session.guard.ts:15–19; apps/api/src/credentials.controller.ts securityEvents; apps/api/src/account-notifications.controller.ts; apps/api/src/email-correction.controller.ts own/withdraw.

The global guard checks durable sessions only when sid exists. Some account endpoints then verify only the JWT signature and subject, without comparing the current user authVersion. A previously valid session-less token can therefore continue reading security events or accessing certain account notifications after logout/password change, until its expiry. Other guards, including GymAccessGuard and SuperAdminGuard, do compare authVersion; this is not a claim that all tenant/admin permissions bypass revocation.

A characterization probe confirmed that a session-less token reaches securityEvents even when the supplied session service would reject it. The probe used synthetic signing material, not a stolen real token. Current normal login issues sid, so exploitation requires possession of an older signed token.

Fix: retire session-less tokens and require an active durable session on protected endpoints. Make public routes explicit and deny protected access centrally. If a transition window is truly needed, give it a fixed cutoff and check user authVersion on every legacy request. Test logout/password change against every account route, not only the main gym guard.

### S3 — Low / defense in depth: token expiry is not mandatory

Evidence: apps/api/src/auth-token.ts:22–36.

The verifier validates exp when present but does not require exp or iat and does not cap token age. A synthetic correctly signed token with neither expiry nor sid was accepted in the review probe. Normal login does set a 15-minute expiry. An attacker cannot remove those claims from a real token without invalidating its signature. This is a verifier-contract weakness relevant to accidental alternate issuers, old tooling, or signing-key compromise; it is not unauthenticated forgery.

Fix: require exp, iat and sid; enforce the expected lifetime and reject malformed/future timing claims. Add explicit missing-claim and overlong-lifetime tests.

### S4 — High availability / Medium abuse-control risk: shared and process-local rate limits

Evidence: apps/web/src/app/actions.ts login fetch; apps/api/src/app.module.ts:70; apps/api/src/auth.controller.ts login throttle. Installed throttler implementation tracks req.ip and defaults to in-memory storage.

Browser requests are sent upstream by the web server without a trusted per-client identifier. The API consequently groups users behind that server into the same login allowance. A small burst of requests can deny login to unrelated people. Counters also differ between API processes and reset on restart. No account-based distributed failed-login control was found.

Fix: establish a trusted web-to-API client identity mechanism, reject spoofed forwarding headers, share counters across instances, and use complementary account/client limits with careful recovery behavior. Bound expensive password work. Test several independent users behind one web process and requests spanning two API processes. Do not merely raise the threshold or blindly enable trust proxy.

### S5 — Medium hardening gap: privileged accounts rely on passwords alone

Evidence: apps/api/src/auth.controller.ts; apps/api/src/identity/credential.service.ts issueOperatorRecovery; packages/contracts/src/credentials.ts. No MFA/passkey implementation was found.

Super Admin controls platform operations and can issue recovery credentials for other accounts, including other admins. Recovery does require the operator's current password, records a verification attestation, and cannot target that same operator. Those are useful controls, but stolen operator credentials remain enough to invoke broad powers. Staff recovery tokens are returned to staff, so authorised staff necessarily have the power to reset eligible accounts; audit records do not prevent misuse.

Fix: require MFA for Super Admin and preferably owners, step-up verification for sensitive operations, independent checks for admin-account recovery, and account-holder notification through a verified channel. Document who can reset whom. Treat this as an explicit trust decision, not an already-proven unauthorized reset exploit.

### S6 — Medium hardening gap: no application-defined framing/script policy

Evidence: apps/web/next.config.ts; apps/web/src/proxy.ts; apps/api/src/main.ts.

No Content-Security-Policy or frame-ancestors/X-Frame-Options policy was found in application response configuration. An upstream hosting layer might add it, which was not inspected. Missing framing restrictions allow pages to be embedded; actual authenticated clickjacking also depends on cookie and browser restrictions. SameSite=Lax reduces some cross-site cases. Missing CSP is not itself proof of an XSS bug.

Fix: set frame-ancestors 'none' unless embedding is intentionally required; introduce a tested CSP compatible with the app's scripts, fonts and images; define Referrer-Policy and nosniff. Verify actual response headers and browser behavior. Keep the existing Origin checks and secure cookies.

### S7 — Medium configuration risk: weak sample secrets and broad database credentials are accepted

Evidence: .env.example; apps/api/src/auth-token.ts; apps/api/src/database-pool-config.ts; apps/api/src/tenant-database.service.ts.

The example JWT value exceeds the verifier's minimum length, so length validation alone accepts that publicly known example. The example also uses the same database login for master, tenant and provisioning access. A single tenant runtime connection template changes only the database name, so physical separation does not give independent runtime credentials per gym.

This review did not read or disclose real secret values and does not claim the sample is currently deployed. The risk is copying development configuration into a shared environment. Compromise of an API runtime holding broad database privileges can affect many gyms.

Fix: reject known placeholders at production startup, generate random secrets, separate API and provisioning credentials, and validate actual database grants. Remove database/role creation privileges from serving processes. Require appropriately verified encrypted database transport for remote connections. Decide whether finer per-tenant credentials are necessary for the threat model.

## Privacy decision requiring product agreement

apps/api/src/coaching/coaching.service.ts:35–43 and 181–203 allow a trainer with a qualifying relationship to view health notes, emergency contact, date of birth, phone and email. A completed session within the previous 90 days qualifies. The query is scoped to the verified trainer/member relationship; no cross-trainer bypass was demonstrated.

Confirm whether a trainer should retain all these fields for 90 days. If not, shorten the relationship window and split coaching information from emergency/identity information. Audit sensitive reads where appropriate. This is policy review, not a proven permission bug.

## Protections observed

- Argon2id password hashing, bounded password inputs, and current-password checks for sensitive credential operations.
- JWT signature algorithm allowlist, issuer and audience checks; current login tokens expire after 15 minutes.
- Hashed refresh tokens with rotation, concurrency grace, idle/absolute expiry, and replay handling for the immediately preceding token. Historical token-family replay detection was not exhaustively verified.
- Durable session revocation and authVersion changes on password changes/recovery; scope caveat in S2.
- Recovery uses random single-use credentials, expiration, bounded failed attempts, issuer authority rechecks and transactional redemption.
- GymAccessGuard verifies identity, active gym access, role, enrollment operation, reciprocal tenant actor and tenant binding. Members/trainers are not authorised merely because they know a record ID.
- Trainer client reads explicitly require a qualifying relationship; sensitive response schemas limit returned fields.
- Parameterized Prisma/raw SQL in reviewed paths; controlled database identifier interpolation uses restrictive validation. No unsafe raw Prisma query API use was found in source search.
- Strict input schemas reject extra fields; CSV export escapes formula-like content.
- HttpOnly cookies, Secure in production, SameSite=Lax; credentials are not stored in localStorage in reviewed paths.
- Web mutation proxy requires the configured Origin and rejects cross-site requests; production requires GYMOS_WEB_ORIGIN. No-store headers protect private responses.
- Support context restricted to scoped summaries/exit with audit and revalidation; no general impersonation capability established.
- Current tracked environment-file check found .env.example, not the local .env. This is not a full git-history secret audit.

## Evidence and follow-up

Identity integration: 18 tests passed against an owned disposable PostgreSQL environment, including consent binding, recovery, session rotation, logout and revoked-owner cases.
Focused unit/characterization: 19 tests passed across six files. Two tests characterize undesirable acceptance rather than prove the desired policy. The review-only probe is retained as characterization-probe.ts.txt outside test discovery.
Application integration: 4 tests passed against an owned disposable database, covering duplicate identity handling, private-note filtering, scoped application status and competing approval/rejection. Total for this review: 41 passing tests. No deployed environment was tested.

Recommended order: verify email ownership; centralize session enforcement and remove legacy acceptance; correct rate limiting; add privileged MFA/recovery controls; add browser headers and production configuration validation. Then run a full HTTP role/resource matrix and browser security tests, including CSRF, framing, stale sessions, user-supplied text and multi-process races. Preserve the operation/tenant-binding protections while fixing these findings.
