# Internal operation and receipt foundation — GYMOS-MIG-004

These primitives extend the separate Master/tenant schemas. They introduce no controller, app-module registration, provisioning worker, tenant routing bypass or financial business implementation. Future callers must authorize the original actor and resolve/gate the exact selected tenant before using them. Raw Operation rows contain private target metadata and must never become HTTP DTOs; return the validated safe result/status projection instead.

`OperationFoundationService.claim` computes a versioned canonical digest and claims an immutable scope/key before feature duplicate checks. Provisioning keeps `provision-gym:<slug>` and one server-generated database name/pinned template. A partial unique index also prevents the same initiator/key being reused under another slug. M.Operation stores exact map states; committed step evidence cannot be changed or expanded later. Scalar enrollment-operation references from003 remain scalar until the owning insertion/activation workflow can maintain them safely.

Acquire a30-second database-clock lease, renew every10seconds through `createLeaseHeartbeat`, and use the returned current lease version for checkpoints. A stale/expired lease cannot mutate the operation. A subsequent attempt requires `reconcileLease` with an authoritative read-only target/receipt verifier before proceeding; verification runs outside a Master transaction, followed by a new lease/version CAS transaction. Task005 provides installed-schema/binding verification;021–023/031/036 own external provisioning/enrollment recovery. This foundation never interprets lease expiry as permission to recreate a database or repeat business effects. REPAIR_REQUIRED/FAILED_FINAL are fail-closed; a separately authorized repair workflow must reconcile them explicitly.

Master checkpoint effects and deterministic ma1 audit commit together. GYM_RESERVED validates the linked Gym slug/database name against the immutable operation target after the local callback; any owner theme must belong to that Gym. Callbacks perform Master-local work only. mv1 audit helper must be called in the same Master transaction as the caller's aggregate CAS; its event key does not implement arbitrary command-result replay.

`CommandReceiptFoundationService.execute` claims all unique receipt/source-operation keys, then performs local business callback, required audit and COMMITTED safe result in one tenant transaction. Required notification inserts, where commissioned, belong in that same callback/transaction. Ordinary retry reuses a committed receipt without calling business effects; changed intent conflicts. Domain constraints must independently reject different-key duplicate terminal intent. Normal execution cannot durably leave a RUNNING receipt because claim and finalization are atomic. Encountering a preexisting RUNNING/REJECTED row requires explicit feature recovery; it never blindly invokes effects again. This is not a generic business reconstruction or authorization service.

Audit keys exactly implement ta1/ma1/mv1 canonical tuples from Database map §7.3. Different content at one event key is an integrity failure. Audit transitions are restricted to status/version metadata, with no health/credential text. SQL blocks audit rewrites and operation/receipt deletion; there is no automatic pruning in this tranche. Future reviewed retention changes must preserve financial origin uniqueness.

Canonical request JSON rejects credential/private keys, accessors, cycles, unsupported values and unsafe integer numbers. Monetary feature DTOs still use exact decimal strings. Compatible secret-bearing legacy commands must supply a separately keyed HMAC intent fingerprint without storing raw credentials. `safeResult` uses a positive field allowlist; credentials, targets, arbitrary data and private health fields never replay. Feature DTOs and current authorization remain separate responsibilities.
